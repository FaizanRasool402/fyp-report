\chaptertitlepage{System Design}

This chapter shows how the method from \textbf{Chapter~3} was turned into working software. The system has five layers: the user interface (HTML/CSS/Jinja), the application (Flask routes), the prediction service (lazy loading, locking and the ensemble), the saved models (\texttt{weights/}), and an offline training pipeline in \texttt{training/}.

\section{System Architecture}

When a user uploads an image, a Flask route receives it and the chest X-ray check makes sure it is a valid X-ray. Then \texttt{predict\_all()} in \texttt{predictors.py} runs EfficientNetB3, DenseNet121 and the Custom CNN on it. Their outputs are combined with soft voting, and the result page shows the probability bars and whether the models agree.

\begin{figure}[H]
\centering
\includegraphics[width=0.92\textwidth]{images/diagrams/fig_system_inference.png}
\caption{High-level inference flow for the unified four-class web application}
\label{fig:sys-arch-flow}
\end{figure}

Every trained four-class model scores every upload, always using the same label order: Normal, Tuberculosis, COVID-19, Pneumonia. Soft voting takes the average of the probability outputs. Old single-disease \texttt{.h5} files are rejected if they do not have four outputs, and if a weight file is missing the app reports it instead of crashing.

\section{Functional Requirements}

\begin{enumerate}
    \item Accept PNG/JPG/JPEG uploads (maximum 16\,MB).
    \item Check that the image is likely a chest X-ray; let the user override this, with a warning.
    \item Run every available 4-class model on the same image.
    \item Show the probability of each class for each model.
    \item Calculate and show the soft-voting result and whether the models agree.
    \item Show a clear error if weight files are missing or do not have four outputs.
    \item Provide offline training scripts that can rebuild the weights from the manifest.
\end{enumerate}

\section{Non-Functional Requirements}

\begin{itemize}[label={}, leftmargin=0pt]
    \item \textbf{Reproducibility:} A fixed seed and a saved manifest, so results can be repeated.
    \item \textbf{Usability:} One upload is enough; the user does not have to pick a model.
    \item \textbf{Robustness:} Images that are not X-rays are rejected in several stages.
    \item \textbf{Consistency:} The app processes images the same way as training.
    \item \textbf{Maintainability:} The class order (\texttt{CLASSES}) is defined once in \texttt{training/common.py}.
    \item \textbf{Safety messaging:} A clear note that the tool is for research only and not for clinical use.
\end{itemize}

\section{Tools and Technologies Used}

We used Python (3.9 or newer; 3.11 is recommended for recent TensorFlow), TensorFlow and Keras, OpenCV, Flask and Werkzeug, NumPy, scikit-learn (for evaluation), Matplotlib and Seaborn (for figures), HTML/CSS and Git. Training is best done on a machine with a good GPU. Prediction can run on a CPU, but it is slower. The main folders are \path{training/}, \path{Frontend/}, \path{weights/} and the three public dataset folders described in \textbf{Chapter~3}.

\section{Chest X-Ray Validation Gate}

\begin{enumerate}
    \item \textbf{Monochrome or tint check:} the image must be grayscale or have a single colour tint (blue-tinted screens are allowed).
    \item \textbf{Radiograph envelope:} the image's brightness, entropy, midtones, shape, symmetry and similar measures must fall in the normal X-ray range; one measure is allowed to fail.
    \item \textbf{Anatomy check:} the image is rejected only if there is no bright central column (the spine) and no left--right symmetry.
\end{enumerate}

\begin{figure}[H]
\centering
\includegraphics[width=0.92\textwidth]{images/diagrams/fig_xray_gate.png}
\caption{Three-stage chest X-ray validation gate with optional forced analysis}
\label{fig:xray-gate}
\end{figure}

We tested the check on a labelled set of 351 real X-rays and 106 images that were not X-rays. It accepted all of the real X-rays (100\%) and rejected about 77\% of the non-X-rays, compared with about 21\% for the old check that only looked at whether the image was monochrome. The user is told why an image was rejected, and the ``Analyse anyway'' option is protected against path traversal.

\section{Application Flow and User Interface}

The home page shows which models are loaded and ready. The user uploads an X-ray through a simple form. The result page shows the probability bars, a short note about each class, the ensemble verdict, whether the models agree, and a warning if the user chose ``Analyse anyway''. \section{Train/Serve Consistency}

The app reads images exactly as training does, with bilinear resizing and the same \texttt{preprocess\_input} or division by 255. Training, evaluation and the user interface all use the same \texttt{CLASSES} order. Weight files that do not have four outputs are refused.

\section{Summary}

The system design turns the method into a research demo that people can actually use. It checks uploads more safely, always runs all the models, combines them with soft voting, and processes images in the app exactly as they were processed during training.
