\chaptertitlepage{System Design}

This chapter describes the software built on that methodology. It has five layers: the presentation layer (HTML, CSS, and Jinja templates), the application layer (Flask routes), an inference service that loads models on first use, guards them with a lock, and computes the ensemble, the model files in \texttt{weights/}, and an offline training pipeline in \texttt{training/}.

\section{System Architecture}

When a user uploads an image, a Flask route receives it and the chest X-ray gate checks it. \texttt{predict\_all()} in \texttt{predictors.py} then scores it with EfficientNetB3, DenseNet121, and the custom CNN, and the soft-voting ensemble combines their outputs. Finally, the results page shows the probability bars and whether the models agree.

\begin{figure}[H]

\caption{High-level inference flow for the unified four-class web application}

Every trained four-class model scores every upload, always with the class order Normal, Tuberculosis, COVID-19, Pneumonia, and soft voting averages their probability vectors. The server refuses old single-disease \texttt{.h5} files whose output is not four classes wide. If a weight file is missing, it reports the problem and keeps running.

\section{Functional Requirements}

\begin{itemize}
    \item \textbf{FR1:} Accept PNG/JPG/JPEG uploads (maximum 16\,MB).
    \item \textbf{FR2:} Validate likely chest radiographs; allow forced override with warning.
    \item \textbf{FR3:} Run every available 4-class model on the same image.
    \item \textbf{FR4:} Display per-class probabilities per model.
    \item \textbf{FR5:} Compute and display soft-voting ensemble and agreement.
    \item \textbf{FR6:} Show clear errors if weights are missing or have wrong output width.
    \item \textbf{FR7:} Provide offline training scripts to rebuild weights from the manifest.
\end{itemize}

\section{Non-Functional Requirements}

\begin{itemize}
    \item \textbf{NFR1 Reproducibility:} Fixed seed and committed manifest policy.
    \item \textbf{NFR2 Usability:} Single upload; no model picker required.
    \item \textbf{NFR3 Robustness:} Multi-stage rejection of non-X-ray uploads.
    \item \textbf{NFR4 Consistency:} Train/serve preprocessing alignment.
    \item \textbf{NFR5 Maintainability:} Shared \texttt{CLASSES} order in \texttt{training/common.py}.
    \item \textbf{NFR6 Safety messaging:} Explicit research-only / non-clinical disclaimer.
\end{itemize}

\section{Tools and Technologies Used}

The system is written in Python (3.9 or later; 3.11 is recommended for current TensorFlow). It uses TensorFlow and Keras, OpenCV, Flask and Werkzeug, NumPy, scikit-learn for evaluation, Matplotlib and Seaborn for figures, HTML and CSS, and Git. Training is best done on a machine with a capable GPU. Inference also runs on a CPU, only more slowly. The main folders are \path{training/}, \path{Frontend/}, and \path{weights/}, along with the three public dataset folders described in Chapter~3.

\section{Chest X-Ray Validation Gate}

Before any model sees an upload, the gate checks it in three stages:

\begin{enumerate}
    \item \textbf{Monochrome or tint check.} The image must be grayscale or a single tint. Blue-tinted display captures are allowed.
    \item \textbf{Radiograph envelope.} Statistics such as intensity, entropy, midtones, aspect ratio, and symmetry must look like those of a real radiograph. One violation is forgiven.
    \item \textbf{Anatomy veto.} The image is rejected only if it lacks both the bright central-column cues and the left-right symmetry cues.
\end{enumerate}

\begin{figure}[H]
\centering
\includegraphics[width=0.92\textwidth]{images/diagrams/xray_gate_pipeline.png}
\caption{Three-stage chest X-ray validation gate with optional forced analysis}
\label{fig:xray-gate}

We tested the gate on a labelled set of 351 real radiographs and 106 other images. It accepted all of the real radiographs and rejected about 77\% of the non-X-rays, where the earlier monochrome-only check rejected only about 21\%. When the gate rejects an image it tells the user why, and the Analyse anyway option is protected against path traversal.

\section{Train/Serve Consistency}

At inference, the application decodes and resizes images exactly as training did, with bilinear interpolation and the same \texttt{preprocess\_input} or $/255$ rescaling. Training, evaluation, and the user interface all take the class order from one shared \texttt{CLASSES} list, and the application refuses any weight file that does not output four classes.

\section{Summary}

The system turns the methodology into a research demo that people can use. It checks uploads before they reach the models, scores every image with all three models, combines them by soft voting, and preprocesses images the same way in the live application as in training.
