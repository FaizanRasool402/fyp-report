\chaptertitlepage{Methodology}

This chapter explains how the system was built and tested. The goal was not only to classify lung diseases from chest X-rays, but also to compare three deep learning models fairly, with all of them trained under the same conditions so the results can be repeated. The work has six steps: combining the datasets, preprocessing and augmentation, designing the models, training, evaluation (including a leakage check), and deploying the models in a Flask app that combines their results.

\section{From Single-Disease Models to a Unified Benchmark}

In an earlier version of this project we had three separate models, each with its own labels: a two-class tuberculosis model, a multi-class COVID-19 model (which used to include Viral Pneumonia), and a two-class pneumonia model. These models could not be compared properly, because any difference in results might come from the datasets and not from the models themselves. In the new method, the task becomes a single four-class problem. All three architectures are trained on the same merged dataset, with the same patient-grouped splits, the same classification head design (for the transfer models) and the same training budget. The label order is fixed as Normal, Tuberculosis, COVID-19, Pneumonia. Viral Pneumonia images from the COVID sources are added to Pneumonia, because the Kaggle pneumonia dataset mixes bacterial and viral cases and they cannot be separated afterwards.

\section{Data Collection and Unified Manifest}

We did not collect any new private clinical data. A script (\path{training/build_manifest.py}) combines three public datasets into one file, \path{training/manifest.csv}. For every image this file stores the path, the class label, the patient ID, the source dataset and whether it belongs to the training, validation or test set.

\subsection{Rules for a Fair Data Split}

\begin{enumerate}
    \item \textbf{Remove duplicate images.} If the exact same image appears twice, only one copy is kept. This stops the same image from being in both the training and the test set.
    \item \textbf{Keep each patient in one set.} All images of one patient go into only one set (training, validation, or test), never into two.
    \item \textbf{Give every patient a unique ID.} Different COVID folders reuse the same file names (for example \texttt{0101.jpeg}), so the folder path is added to each ID to keep patients apart.
    \item \textbf{Take Normal and Pneumonia from more than one dataset.} This stops a model from guessing the class just by recognising which dataset an image came from.
    \item \textbf{Limit large classes and use class weights.} COVID-19 has only 130 images after removing duplicates. The other classes were limited to 1{,}200 images each (\texttt{-{}-cap 1200}). Class weights give the smaller classes more importance during training (COVID weight $\approx$ 2.851).
    \item \textbf{Check classes against sources.} Training starts only after confirming that Normal and Pneumonia images come from more than one dataset.
\end{enumerate}

All images come from public research datasets. The system is a research demo and a comparison of models. It is not a clinically tested diagnostic device.

\subsection{Augmentation and Class Imbalance}

All models get the same geometric augmentation (rotation, shifting, zoom and horizontal flip, each within set limits) through the shared data pipeline. We did not oversample the disease images. Instead, class weights based on how rare each class is are used with categorical cross-entropy, so that mistakes on the smaller classes count for more.

\section{Model Architectures and Shared Head}

The models are defined in \texttt{training/models.py}. Both transfer models use the same head, so that the comparison measures the backbone and nothing else:
\[
\text{GAP} \rightarrow \text{Dropout}(0.5) \rightarrow \text{Dense}(256,\text{ReLU}) \rightarrow \text{Dropout}(0.3) \rightarrow \text{Dense}(4,\text{softmax}).
\]
Every model uses a softmax output with categorical cross-entropy. This fixes an earlier mistake where a sigmoid output was paired with a categorical loss. None of the models start from the old single-disease weights.

\begin{figure}[H]
\centering
\includegraphics[width=0.95\textwidth]{images/diagrams/fig_model_architectures.png}
\caption{Three architectures scored under a matched four-class protocol (shared head for transfer models)}
\label{fig:model-arch}

\textbf{EfficientNetB3.} Uses an ImageNet backbone. In Phase~2, layers from 340 onwards are unfrozen ($\sim$42.7\% of the parameters).

\textbf{DenseNet121.} Uses an ImageNet backbone. In Phase~2, layers from 300 onwards are unfrozen ($\sim$42.8\%). The BatchNorm layers stay frozen during fine-tuning.

\textbf{Custom CNN.} Five convolution blocks (filters $32\rightarrow64\rightarrow64\rightarrow128\rightarrow256$) with BatchNorm, pooling and dropout, ending in a four-class softmax. It is trained from scratch and serves as a baseline.

\section{Evaluation Methodology}

The script \path{training/evaluate.py} tests every model on the held-out test set. It reports accuracy, balanced accuracy (the average recall over the classes), precision, recall and F1 for each class, confusion matrices, a comparison between the models, and the results of the soft-voting ensemble. These are saved to \path{training/results/comparison.md}. Soft voting takes the average of the models' probability outputs and picks the class with the highest value. Unlike a simple majority vote, it keeps information about how confident each model is.

\begin{figure}[H]
\centering
\includegraphics[width=0.95\textwidth]{images/diagrams/fig_evaluation.png}
\caption{Evaluation flow: matched test scoring, ensemble soft voting, and source-leakage probe}
\label{fig:eval-flow}
\end{figure}

The script \texttt{training/leakage\_probe.py} trains a classifier that tries to guess which dataset an image came from, and compares it with a simple majority baseline. A result close to the baseline is what we want. If the source could be predicted almost perfectly, it would be a warning that TB or COVID-19 might be recognised from how the images were taken rather than from the disease. COVID-19 recall is still the main weak point, because there are so few COVID-19 test images.

\section{Application Integration Workflow}

In the app, the flow is: upload (PNG/JPG/JPEG, up to 16\,MB) $\rightarrow$ three-stage chest X-ray check (or ``Analyse anyway'') $\rightarrow$ \texttt{predict\_all()} $\rightarrow$ soft-voting ensemble $\rightarrow$ result page with a probability bar for each model, the final verdict and whether the models agree. The model weights must have four outputs, and old \texttt{.h5} files are rejected. The full sequence for running the project is: \path{build_manifest.py} $\rightarrow$ \texttt{train.py -{}-model all} $\rightarrow$ \path{evaluate.py} $\rightarrow$ (optional) \path{leakage_probe.py} $\rightarrow$ \path{Frontend/app.py}.

\section{Methodological Validity and Limitations}

The method is sound because the task is clearly defined, there are controls against leakage, the models are trained under the same conditions, the metrics include recall for each class, and the app processes images the same way as training. It also has known limitations. The public datasets are small. COVID recall is not statistically stable. Four-class accuracy is expected to be lower than the older two-class figures. TB and COVID images each come from a single source, so a model could still take shortcuts (which is why we run the probe). The system is not a clinical device, and Grad-CAM and testing on data from several hospitals are left for future work.

\section{Summary}

In short, this method turns three previously separate detectors into one four-class comparison of three models that guards against leakage and is deployed as an ensemble. The comparison is fair because all models share the same data and training setup, and the evaluation is open about the limits of the datasets and the fact that this is not a diagnostic tool.
